# Alternative diversity and individual design validity

案を生成した事実、案が違うこと、各案が妥当なことを分けて評価する。
複数agent、違う名前、違う工数だけでは、多様性も妥当性も証明されない。

## 1. Pairwise diversity: 変更案の全ペアを比較する

新規は変更案3つ以上で全ペア（3案なら3、4案なら6）を評価する。P0は別に残す。
2案1ペアは旧結果の読込みに限る。alternativesは同じ目的・契約・scopeを前提にする。
portfolioは全体目的・契約を共有し、領域ごとの目的・scopeを明示して評価する。
その違いを不当な比較とみなさず、領域内の方式差と領域間の改善対象の差を区別する。
次の設計判断がどう違うかを具体化する。

| axis | 実質差を確認する問い |
|---|---|
| responsibility | 責務・state・ルールの所有者と境界が違うか |
| dependencies | 依存の向き・共有範囲・結合点・障害伝播が違うか |
| contract | 内部契約や互換boundaryの置き方が違うか。必須の外部契約は保つか |
| migration | 共存・切替単位・途中状態・互換期間が違うか |
| recovery | 戻す単位、不可逆性、rollback/forwardの成立条件が違うか |
| complexity | abstraction・runtime/build時の仕組み・運用負担が実際に違うか |

名前・言い換え・見積値・順序番号・file名だけの差をaxisへ数えない。
最終構造が同じでも、配布・共存・復旧の戦略が変われば実質差になり得る。
逆に工程を細かく分けただけなら、移行戦略が違うとは限らない。
外部契約を壊した差を、妥当な多様性として褒めない。個別妥当性でも検出する。

### Pair verdict

- `distinct`: 少なくとも一つの重要な設計判断に、選択を変え得る実質差がある。
- `overlapping`: 中核は同じで一部の差はあるが、独立した方針として弱い。
- `duplicate`: 重要な設計判断は同じで、説明や値だけが違う。
- `unknown`: 構造・移行の記述不足等で判断できない。

`distinct` でも共有点を記す。差があることは、優れていることや違う目的を解いて
よいことを意味しない。別案の数を増やすためduplicateをdistinctへ昇格させない。
duplicateの二案がどちらも妥当な設計という場合はあり得るが、二つの独立した選択肢
として数えない。一方を無効設計と決めつけず、統合するか方針を再設定する。

## 2. Individual validity: 各案を他案から独立して評価する

P0も含め、各案に次の六項目を一回ずつ評価する。差分の大きさや工数の安さで
設計上の破綻を相殺しない。P0は「基準として妥当か」を見て、目標未改善は別記する。

| criterion | 静的な計画として確認すること |
|---|---|
| goal_fit | 目的に因果的に寄与するか。未達・余分なscope・必要性を正直に説明するか |
| responsibility | cohesion、所有権、一貫したルール配置。根拠のない共通化・過剰抽象でないか |
| dependencies | 依存方向、循環、caller、共有障害点、layer境界を扱っているか |
| contract | 公開API、戻り値、エラー、副作用、丸め、データ・権限等を保存できる計画か |
| migration | 実行可能な依存順・途中状態・共存・配布・廃止条件があるか |
| verification_recovery | 差を検出する将来検証と、条件付きの復旧・不可逆性の説明があるか |

checkは `pass / conditional / fail / unknown` と理由・根拠IDを持つ。
「実装してテストが通ったか」ではなく「成立する設計・検証計画か」を見る。
未実施テストだけを理由に全案を無効化しないが、保存を断言もしない。
工数履歴不足は経済評価のunknownであり、それだけでarchitectureが無効にはならない。
重大な契約違反、循環依存、実行不能な移行、目的に反する構造はfailにする。

### Overall validity

- `plausible`: 六項目すべてpass。静的な計画として筋が通る。実装成功の証明ではない。
- `conditional`: failはなく、必要条件・重要な未解決点が残る。条件を列挙する。
- `invalid`: 一つ以上failがあり、現在の案のままでは成立しない。修正または棄却する。
- `unknown`: failを立証したわけではないが、重要な情報不足で設計を判定できない。

failがあるのにplausibleとしない。条件が残るのに全面的に妥当としない。
判定を0〜100点や自信の確率に換算せず、具体的な理由で人間に返す。

portfolioは当該領域へのgoal_fitを評価し、一案だけで全領域を解決しないことをfailにしない。
依存・移行・回復には他候補と接する境界、併用条件と重複する作業も含める。
各案がplausibleでも、組合せがそのまま安全・費用加算可能とは限らない。

## 3. Critic output and action

`critique_result.design_review` に `version: "1.0"`、全変更案ペアの `pairwise`、
P0を含む全案の `plans` を入れる。型は同梱schemaを正本にする。
各pairにplan IDs、判定、axisごとの具体差・根拠、理由を記す。
各planに総合判定、六checkと理由・根拠、残る条件を記す。

不備は既存 `findings` にも具体的な修正要求として出す。親は重大な不備を担当へ返し、
修正後の正確なplan revisionを再確認する。invalid案は推薦しない。
多様性不足は個別の妥当性と区別し、最低3候補のうち実質差を確認できた数を正直に示す。
新しい出力ではこのreviewを必須にし、旧packetで欠ける場合は「設計評価なし」と表示する。
旧packetを読み込めることは、その設計評価が済んでいたことを意味しない。

## 4. Presentation

数値比較に先立ち、以下を人間の言語で示す。

1. 全ペアの「共通点／実質差／判定」。
2. 各案の六項目の評価、総合判定、根拠、成立条件・修正点。
3. 違うが無効な案、妥当だが重複する案、妥当でも目的に過剰な案を区別する。

評価器自身も、名前だけ違う案、契約を壊す案、情報不足の案、妥当な別案という
正負の対照で試す。LLM judge同士の同意や自己申告だけを検証とみなさない。
