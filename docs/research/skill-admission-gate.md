# スキル入場ゲート（gate-skill-candidates）の構築・実測・削除の記録

2026-08 に構築し、実測に基づいて同月に削除したスキル admission gate の設計知見と実証データの記録。スキル本体は git 履歴（commit `89d17ca` 時点の `skills/gate-skill-candidates/`）に残っている。以下の判定手続きは、スキルとしてではなく**明示的に依頼して使う思考ツール**として引き続き有効。

## なぜ作ったか

スキル追加には見えない恒常コストがある。全スキルの metadata（name + description）は毎セッション読み込まれ（Anthropic 公式: 「コンテキストウィンドウは公共財」）、インベントリが増えるほど description ベースのスキル選択の精度が全スキルで劣化する。一方でモデルは「スキルにして」と言われると審査ゼロで作る。この非対称を塞ぐ default-deny の入場審査として設計した。

## 5つのダイヤル（再利用可能な判定手続き）

各ダイヤルは pass/fail ＋証拠行必須。証拠なしの合格は不合格。判定はラベルではなく行き先の割り当て: `skill` / `merge-into-existing-skill` / `project-memory`（常時読み込みファイルへ≤3行を起草） / `reference-doc-only` / `no-build` / `split`（部分ごとに別の行き先）。

1. **再発性** — プロジェクト・セッション横断で繰り返すか。実際に起きた/確実に予見される機会2件以上。「いつか使うかも」は不合格
2. **行動差分** — スキルなしの Claude と挙動が変わるか。証拠は**観察された baseline の失敗**（公式の評価駆動開発: 「スキルなしで走らせ具体的失敗を記録せよ」）。「言われればできる」は不合格
3. **トリガー適合性**（双方向） — (a) 発火してはならない具体的発話3件が書けるか（書けない候補は反証不能として即不合格）。(b) 発火してほしい場面は「モデルがスキルを引くに足る複雑さ」か（常時適用の心得・ワンステップの願望はスキルでは発火しない）
4. **最小機構** — project-memory 行・既存スキル追記・reference 文書・何もしない、で足りないか。スキルは最後の手段
5. **文脈コスト対効果** — 発火頻度 × 正解時の価値 vs 常駐税＋全既存スキルへの選択外部性

出典: [Anthropic Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)、公式 skill-creator スキル（「モデルは under-trigger 傾向」「単純なワンステップ依頼は description が完璧でもスキルを引かない」）、[anthropics/skills](https://github.com/anthropics/skills)。

## 実証データ

### 盲検評価（iteration 1–3）

6本の挙動テストをスキルあり/なしで実行し、ゲート語彙を排した結論のみ assertion と、条件を伏せた A/B 判定で再評価した。

- **当初の 92% vs 33% はほぼ同語反復だった**。assertion をゲートの出力語彙（scorecard・routing 表）で書いていたため、同じ結論に達した baseline が形式面だけで落ちていた。format-blind の再採点では 21/21 vs 19/21
- **盲検 A/B は 2勝4敗 → 修正後 3勝3敗**。勝ちは全て「行動差分が実在する場面」: 命令形の構築依頼での事前審査（baseline は審査ゼロで即構築）、オーバーライド時の gate note、統合先まで起草した実行可能な次の一手。負けは全て助言形（「すべき？」）——**モデルは尋ねられれば素の状態でほぼ同じ判定をより簡潔に出す**。手続きの外装（表・在庫列挙・専門語彙）は盲検判定者に一貫して「ノイズ」と評された
- 常時適用の心得の行き先は、盲検判定者が CLAUDE.md（常時読み込み）を「姉妹スキルへの merge（発火時のみ適用）」より上と判定。project-memory を行き先から外す設計は実測で覆った

### 発火実測（削除を決めたテスト）

skill-creator の `run_eval.py`（description を available_skills に載せ、素の `claude -p` でスキルが読まれるかを検出）で計測。

- 添付物なしのクエリ（「**この**チェックリストをスキルにして」等）は 0/39 —— ただしこれはモデルが明確化質問で終わるための**計測無効**（クエリの欠陥）
- 実体を含む手動プローブ 1回は即発火し、正しく審査した（スキル化拒否 → CLAUDE.md 行きを起草）
- **実体を含む有効な決定的2クエリ × 3回の再計測: 1/3 と 0/3**。事前コミットした判定規則（各 2/3 以上で keep、どちらかが 1/3 以下で削除）に該当し削除

## 教訓

1. **ゲートの唯一の実証済み価値は「構築の瞬間の介入」だが、その瞬間にスキルが引かれるかは信頼できない**。「頼まれたら即作る」というゲートが防ぎたい失敗と、「自力でできる作業ではスキルを引かない」という不発火条件は同じもの。価値の発生点が発火の死角にあるスキルは成立しない
2. 確実に届く機構は2つ: **人間自身の一言**（「作る前に審査して」——モデルは頼まれれば審査を上手くやれることは盲検で実証済み）と、**常時読み込みの instruction 行**
3. 自作の eval は自作スキルの出力契約をなぞりがち（同語反復）。format-blind の結論のみ assertion と盲検 A/B で剥がすこと
4. 判定規則は**計測前に事前コミット**すること。計測の妥当性修復（無効クエリの修正）と、不利な結果を見てからの基準緩和は別物であり、前者だけが許される

## 復活条件

モデルの implicit invocation が構築系依頼で信頼できる水準になったら（同じ2クエリ×3回で各 2/3 以上）、`89d17ca` から復元して再入場審査にかける価値がある。
